## 1. 路线 2：安卓手机 + Linux 端口，运行 Linux 版（Termux / PRoot）

### 1.1 架构设计
试图将现有家服跑通的“Xvfb + 原生 Linux 微信 4.1.x + Python WAL 解密流水线”整体打包迁移到一台闲置 Android 手机中，通过 Termux / PRoot（或 Root 后的 Chroot）环境模拟 Linux 发行版常驻运行。

### 1.2 关键技术可行性深度剖析

#### (1) Linux 微信二进制包与架构匹配
- **官方支持**：腾讯官方发布的 Linux 微信 4.0.x / 4.1.x 桌面版（基于 Qt 6 / Chromium 内核重构）**提供了官方原生的 `aarch64` (ARM64) deb 安装包**（主要面向国产统信 UOS / 麒麟麒麟系统 ARM64 设备）。因此在手机 ARM64 处理器上理论上无需 box64 / QEMU-user 等指令集动态翻译，可直接执行原生指令。

#### (2) PRoot / Termux 运行环境的内核级阻碍（致命伤）
虽然指令集兼容，但在 Android 用户空间容器（PRoot/Chroot）中拉起 Linux 桌面微信会遭遇一系列内核与机制硬伤：
1. **Chromium / WebKit 沙盒崩溃**：
   - Linux 微信内置了 Chromium WebKit 引擎用于小程序、文章和公众号渲染。
   - Chromium 强制依赖 Linux 内核的 `user namespaces` (用户命名空间，`unshare(CLONE_NEWUSER)`)、`seccomp-bpf` 过滤以及 `bwrap` (Bubblewrap) 隔离机制。
   - **Android 内核策略**：非 Root 环境下 Android 内核对 unprivileged namespaces 和 ptrace 权限严格收紧；即使加上 `--no-sandbox` 参数启动微信，微信主进程、GPU 渲染子进程以及 CrashPad 监控进程在 PRoot 拦截系统调用时仍会产生高频 `SIGSYS` 或 `SEGV` 崩溃。
2. **PRoot 系统调用模拟开销 (ptrace overhead)**：
   - PRoot 依靠 `PTRACE_SYSCALL` 拦截所有的文件与内存系统调用。
   - 微信多线程网络 I/O、SQLCipher 密文逐页读写、X11 socket 渲染在 PRoot 下被拦截并多次上下文切换，导致 CPU 负载暴增 300%~800%，出现严重假死和消息收发丢包。
3. **D-Bus 与 IPC 服务链缺失**：
   - Linux 微信 4.1.x 强依赖 `dbus-daemon --session` 进行单实例锁（Single Instance Lock）与桌面通知通信。在 PRoot/Termux 中必须手动拉起独立 D-Bus 守护进程并注入 `DBUS_SESSION_BUS_ADDRESS`，缺少 systemd 管理极易出现孤儿进程残留导致启动即报“已有实例在运行”。
4. **X11 虚拟显示与共享内存 (`/dev/shm`)**：
   - Termux 默认没有原生的 `/dev/shm`（tmpfs），而 Xvfb 和 Chromium 共享内存依赖 POSIX shm。未挂载虚拟 tmpfs 会直接导致 Xvfb 创建 display `:99` 失败。

#### (3) 手机端功耗、发热与 Android LMK (Low Memory Killer)
- **内存开销**：Linux 微信（Chromium+Qt 多进程）+ Xvfb + Python 解密环境冷启动占用 **1.1GB ~ 1.6GB RAM**。
- **Android 后台保活机制**：
  - Android 系统自带的 LMK（Low Memory Killer）与 Android 12+ 引入的 **Phantom Process Killer**（限制后台子进程总数最大为 32 个，且监控后台 CPU 持续占用）。
  - PRoot 派生出的 Xvfb、D-Bus、WeChat 主进程、Renderer、GPU Process 会瞬间打满 Phantom Process 限制，在熄屏 5~15 分钟内必然被 Android 内核强制 `SIGKILL` 终止。
  - 要解决此问题，手机必须保持常插电、解锁开发者选项执行 `adb shell device_config put activity_manager max_phantom_processes 2147483647`，并禁用电池激进优化。
- **发热与电池鼓包**：手机在 24 小时后台运行 Chromium + Xvfb 且无主动散热，持续发热会导致电池在 2~3 个月内鼓包，存在硬件安全隐患。

### 1.3 结论判定
> **工程定性：充满内核级天坑的“折腾玩具”**。
> 虽然指令集通畅，但沙盒对抗、系统调用拦截损耗、IPC 残缺及 Android 激进的后台杀进程机制，使得该方案极度脆弱，无法支撑 7×24 小时无人值守高可用运行。

## 2. 路线 1：Root + WeChatPad + 进内存（Android 辅机）

### 2.1 架构设计
采用一台闲置 Android 手机进行 Root（Magisk / KernelSU / APatch），安装 **LSPosed (Zygisk)** 框架，配合针对微信进程（`com.tencent.mm`）的 Hook 模块（如改写的开源 Observatory 模块或自研轻量 Hook）。
关键机制：将微信伪装/激活为 **“平板模式 (WeChatPad)”** 登录。

### 2.2 关键技术可行性深度剖析

#### (1) 现有代码资产与 Android 底层数据结构的断代差异
现有在 Linux 家服沉淀的代码（`wechat_wal.py` / `wechat_publish.py` / `wechat_schema.py`）**无法直接搬到 Android 端读取本地数据库**，原因如下：
1. **数据库引擎不同**：
   - Linux 微信使用的是标准的 **SQLCipher 4.x** 加密 SQLite，加密格式为标准 4096 字节页，HMAC-SHA1/SHA256 校验。
   - Android 微信使用的是腾讯自研的 **WCDB 2.0+**（开源库底层修改版），其引入了页级动态压缩（ZSTD Dict compression）、私有加密头以及拆库分片（`EnMicroMsg.db`、`EnMicroMsg_1.db` 等）。
2. **表结构与映射模式完全不同**：
   - **Linux 桌面版**：采用 `Msg_{md5(username)}` 为每个联系人/群聊单独建表，使用 `Name2Id` 做路由。
   - **Android 移动版**：所有消息集中存放在一张庞大的 `message` 表中，以 `talker`（联系人 wxid / 群聊 id）、`msgId`、`content`、`type`、`createTime` 为字段。
3. **WAL 防撕裂工具不通用**：
   - Android 版 WCDB 的 WAL 机制深度结合了腾讯的 Checkpoint 策略与 MMKV 缓存，直接在文件层做 WAL 解析不如直接在内存中拦截。

#### (2) 真正的解法：LSPosed 内存拦截（Hook 消息分发）
在 Android 辅机上，**无需解析本地数据库**，而是直接在内存层进行事件监听：
- **Hook 点位**：Hook 微信消息接收核心流水线（如 `com.tencent.mm.storage.MsgInfoStorage` 的 `insert()` 方法，或网络回包回调 `NetSceneNewSync`）。
- **数据流向**：一旦有新消息到达，Hook 代码直接从内存对象中提取明文 JSON，通过本地 HTTP/WebSocket 即时推送到中继服务或 Tailscale 私网 API。
- **实时性**：从 Linux 方案的“5 分钟轮询增量”直接跃升至 **“0 毫秒事件驱动（Event-Driven）推送”**。

#### (3) 核心优势：并发席位完美共存（平板模式席位）
微信官方协议的多端登录拓扑对设备类型有明确的“席位划分”：
- **手机席位（Mobile）**：仅允许 1 台（用户的主力手机）。
- **电脑席位（PC/Desktop）**：仅允许 1 台（用户的 Mac / Windows / Linux 电脑）。
- **平板席位（Pad/Tablet）**：仅允许 1 台（iPad / Android 平板 / 折叠屏展开态 / 车机）。

**核心结论**：
当 Android 辅机通过 Hook 注入伪装设备类型为 `WeChatPad` 登录时，它占用的是**独立的平板席位**。
用户的**主力手机（iPhone/Android）+ 主力办公电脑（Mac/Win 笔记本）+ 辅机（WeChatPad）可以实现三端同时在线，绝不互踢！**

```
┌────────────────────────────────────────────────────────┐
│                   微信服务端 (Tencent Cloud)            │
└───────────────┬───────────────────┬────────────────┬───┘
                │                   │                │
          [手机席位]            [电脑席位]        [平板席位] (WeChatPad)
                │                   │                │
        ┌───────▼───────┐   ┌───────▼───────┐┌───────▼───────┐
        │ 用户主力手机   │   │ 用户办公主力机 ││ Android 辅机  │
        │ (日常收发通信) │   │ (Mac/Win 办公)││ (无感抓取监控) │
        └───────────────┘   └───────────────┘└───────────────┘
                                     ▲                ▲
                                     └─ 绝不互踢 ─────┘
```

#### (4) 维护成本与风控特性
- **版本维护**：Android 微信每 2~3 周迭代一个版本，微信全量启用了 ProGuard 代码混淆、Tinker 热补丁与 AndResGuard 资源混淆，类名和方法名每次发版都会剧烈变化。
  - **避坑方案**：在辅机上**彻底禁用应用商店自动更新**，将微信版本固定在特定稳定版（如 8.0.48/8.0.50）。只要版本锁定，Hook 模块便一劳永逸。
- **风控特性**：由于运行在真正的物理手机上（有真实基带、电池状态、Wi-Fi/4G 网络、原生硬件指纹），其在腾讯服务端的风控画像与真实用户完全一致，比 VPS 虚拟化环境安全数个数量级。

## 3. 路线 3：VPS / 闲置 Linux 电脑（复用现有 Linux 家服方案）

### 3.1 架构设计
沿用当前完全成熟的生产级代码库：
`Xvfb :99` + `原生 Linux 微信 4.1.x` + `wcdb_key_tool` + `wechat_publish.py` (WAL 帧合并) + `wechat_export_api.py` (Tailscale 私网 API)。

### 3.2 关键技术可行性深度剖析

#### (1) 技术优势：100% 验证、零边际开发成本、极致可靠
- 核心代码已在生产环境经历实战检验：WAL 二进制帧解析完美解决读撕裂；基于 Tailscale 虚拟局域网的 API 导出具备零信任安全性；systemd 提供严密的进程崩溃自动重启。
- 架构分层清晰，解密与导出完全只读，不触碰微信内存，无封号风险。

#### (2) 致命工程硬伤：PC 登录席位排他性（单点互踢）
微信协议对于桌面客户端（Windows / macOS / Linux 统信版）统一定义为 **`PC Client` 席位**。
协议硬性约束规则：**全网同一时刻，同一个微信账号只允许存在 1 个 PC 席位连接。**

#### 场景推演：
1. **如果监控的是“用户个人主力微信号”**：
   - 用户在家服/VPS 部署了 Linux 微信进行抓取。
   - 当用户在公司打开 Mac 笔记本或 Windows 台式机登录微信办公时，**Linux 家服端的微信会立即被腾讯服务端强制踢下线**（收到登出通知）。
   - Linux 端的微信进程一旦掉线，将停止接收新消息并停止向本地 SQLCipher 数据库写入，抓取流水线彻底瘫痪，直到用户重新扫描二维码。
   - **结论**：用于主力号时，存在无法调和的席位冲突，属于**架构硬伤**。
2. **如果监控的是“小号 / 独立运营号 / 专属客服号”**：
   - 该账号日常不需要在其他电脑上登录办公。
   - Linux 家服可以 24×7 独占该账号的唯一 PC 席位。
   - **结论**：此场景下无任何冲突，运行稳定性达到 99.99%。

#### (3) 基础设施环境差异：VPS（机房 IP）vs 闲置 Linux 电脑（家庭宽带）
- **VPS（云服务器/数据中心）**：
  - **网络风控**：阿里云、腾讯云、AWS、Vultr 等机房 ASN（自治系统编号）在微信安全风控系统中被高度标记。首次登录经常提示“当前网络环境存在异常”无法扫码，或在登录数天后触发安全风控，强制要求手机端辅助验证。
  - **无头维护成本**：一旦会话失效，需要通过 SSH 隧道端口转发或 VNC 远程连接 Xvfb 桌面重新扫码。
- **闲置 Linux 电脑 / NAS（家庭宽带）**：
  - **网络信誉度高**：家庭宽带分配的动态公网/内网 IP 属于普通住宅 ISP，风控信誉极好，长期挂机极少被踢。
  - **内网便利性**：配合 Tailscale 私网互联，可在局域网内任意调用增量 API。

### 明确结论与推荐行动建议：

1. **坚决放弃 路线 2（手机 Termux/PRoot 跑 Linux 微信）**：
   - 这是典型的“逻辑上可行、工程上一堆天坑”的方案。沙盒机制（bwrap/seccomp）与 Android 内核冲突、PRoot ptrace 的高额损耗、Android LMK 激进的后台杀进程机制，注定无法稳定运行，纯属浪费时间。
2. **场景 A：如果要抓取的是【个人主力微信号】 → 必须走【路线 1：Root + WeChatPad】**：
   - 核心诉求是**“主力电脑要办公，辅机抓取不能停”**。
   - 必须利用 WeChatPad 的平板席位优势实现三端并发。技术方案由“离线解析 SQLite”转型为“LSPosed 内存拦截事件推送”，锁定微信稳定版，彻底解决互踢问题。
3. **场景 B：如果要抓取的是【小号 / 运营号】 → 必须首选【路线 3：闲置 Linux 电脑 / 家服 NAS】**：
   - 现有代码（`wechat_wal.py` / `wechat_publish.py` / `wechat_export_api.py`）**已经 100% 跑通并验证**，零开发成本。
   - 部署在家用宽带 Linux 设备上，网络信誉极高，systemd 保活极其稳定，是工程ROI最高的方案。
